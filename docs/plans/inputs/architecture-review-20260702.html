Unify the Session intake pipeline

Strong in-process

Before

prisma.player.create → duplicate

validateSession

two intake paths, divergent resolve + auth

After

Session intake module

resolve · validate · persist · recalc

resolvePlayerName (one path)

validateSession

persist (create | replace)

runRecalculation

submit → intake edit → intake

one interface, two call sites

Problem

Submit reuses an existing Player by name; edit calls prisma.player.create directly - editing a session and typing a "new" name makes a duplicate Player row. Auth is hand-rolled twice.

Solution

One intake module behind a single interface: resolve slots, validate, persist (create or replace), recalc. Submit and edit become two thin callers passing a flag.

Wins

  • - locality: the duplicate-Player bug concentrates in one module
  • - leverage: one resolve path, two call sites
  • - interface shrinks; edit stops reaching into Prisma
  • - tests hit one intake interface, not two actions

After

League read module

ladderFor(slug)

load + recalc + derive behind one interface

Problem

Three pages each borrow RecalcStore.load* (a write-path port), call recalculate inline, then reach into raw Prisma for view data. The "derive the Ladder" knowledge lives in the page, not a module.

Solution

A read module with one method per view (ladderFor, playerTrend, sessionDetail). It owns load + recalculate + derive; pages shrink to call-and-render.

Wins

  • - locality: "how the Ladder is derived" concentrates in one module
  • - leverage: one interface, three pages
  • - RecalcStore stops being borrowed for reads - write port stays write
  • - tests build one read adapter, not a page + store + engine

Problem

requireAdmin() is copy-pasted in three action files - same three lines each. A scorer gate (requireLeagueScorer) exists; an admin gate does not. The edit action hand-rolls a fourth auth (authoriseFor).

Solution

One requireAdmin next to requireLeagueScorer in league-access.ts. Admin actions call it; the edit action's authoriseFor composes it with the ownership check.

Wins

  • - locality: "admin actions require ADMIN" lives in one module
  • - delete three shallow copies
  • - edit auth composes the gate instead of re-deriving it

Concentrate the Scorer grant/revoke adapter

Speculative ports & adapters

Files

lib/league-scorer-store.ts (LeagueScorerStore)
lib/league-provisioning-store.ts (grant/revoke re-declared)
lib/access-request-store.ts (grant re-declared)

Before

scorer-store: grant / revoke
provisioning-store: grant / revoke (copy)
access-request-store: grant (copy)

same upsert, three adapters

After

scorer-store: grant / revoke
provisioning → delegates
access-request → delegates

one adapter, two delegators

Problem

grant/revoke (upsert + deleteMany on LeagueScorer) is implemented three times across three Prisma adapters. The LeagueScorerStore interface exists but the other two stores re-declare the methods instead of composing it.

Solution

The provisioning and access-request Prisma adapters delegate grant/revoke to prismaLeagueScorerStore rather than re-implementing. The pure ports stay separate; only the adapter bodies collapse.

Wins

  • - locality: the upsert idiom lives in one adapter
  • - delete two copies of a three-line method
  • - pure ports unchanged - seam discipline holds
